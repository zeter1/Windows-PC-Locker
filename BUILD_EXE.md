# Сборка Windows PC Locker в EXE

`build_exe.bat` — единственная команда, которую нужно запускать вручную. Двойной щелчок по BAT выполняет полный проверяемый цикл сборки и публикует `dist/` только после успешных тестов готового EXE.

## Самый простой способ

1. Скачайте репозиторий и распакуйте его в обычную папку с правом записи.
2. Дважды щёлкните `build_exe.bat`.
3. Дождитесь сообщения `[OK] READY BUILD CREATED AND VERIFIED`.
4. Используйте файлы из `dist/`.

Готовая поставка содержит:

```text
dist/
├─ Windows-PC-Locker.exe
├─ Windows-PC-Locker-portable-x64.zip
├─ build_info.json
└─ SHA256SUMS.txt
```

Для запуска готового EXE на другом Windows-компьютере Python и PyInstaller не нужны.

## Что именно делает build_exe.bat

BAT остаётся короткой точкой входа и передаёт работу в `tools/build_windows.ps1`. Сборщик:

1. проверяет, что запущен Windows x64/ARM64, проект доступен для записи и есть минимум 2 ГБ свободного места;
2. ищет Python 3.13 x64;
3. если Python отсутствует, в обычном локальном режиме сначала использует `winget`, а затем имеет резервный путь через официальный подписываемый установщик Python 3.13.15 с обязательной проверкой SHA-256;
4. создаёт отдельное `.build-venv` и не засоряет обычный Python проекта;
5. устанавливает зафиксированный build toolchain из `requirements-build.txt`;
6. выполняет `pip check`;
7. компилирует `computer_locker.pyw`;
8. запускает безопасный source `--self-test`;
9. генерирует Windows manifest: `asInvoker`, DPI awareness и long-path awareness;
10. добавляет Windows FileVersion/ProductVersion/ProductName в свойства EXE;
11. собирает `onefile` через PyInstaller без UPX;
12. проверяет минимальный разумный размер EXE;
13. запускает `--self-test` собранного EXE с жёстким 60-секундным timeout;
14. копирует EXE в отдельную временную папку с пробелами и кириллицей и повторяет self-test;
15. создаёт portable ZIP;
16. распаковывает ZIP в новый временный каталог, сверяет SHA-256 EXE и ещё раз запускает packaged self-test;
17. формирует `build_info.json` и `SHA256SUMS.txt`;
18. только после всех проверок атомарно заменяет `dist/`.

Если новая сборка ломается до финальной публикации, существующий рабочий `dist/` не заменяется.

## Резерв предыдущей рабочей сборки

Перед публикацией новой проверенной версии старый `dist/` переносится в:

```text
dist_previous/
```

Если финальная публикация не удаётся, сборщик пытается вернуть предыдущий `dist/` обратно.

## Режимы

### Обычная полная сборка

```bat
build_exe.bat
```

Это рекомендуемый режим перед передачей программы другому человеку.

### Быстрая повторная сборка

```bat
build_exe.bat --fast
```

Переиспользует совместимое `.build-venv` и PyInstaller work cache. Критические проверки готового EXE, portable-папки и ZIP всё равно выполняются.

### Полностью чистая сборка

```bat
build_exe.bat --clean
```

Удаляет build-окружение и кэш и собирает заново. Текущий рабочий `dist/` при этом сохраняется до момента успешного окончания новой сборки.

### Только диагностика среды

```bat
build_exe.bat --diagnose
```

Проверяет Windows, архитектуру, место на диске, права записи и наличие подходящего Python. Не устанавливает зависимости и не собирает EXE.

### CI

```bat
build_exe.bat --ci
```

Режим GitHub Actions/Codex: нет `pause`, корректные exit codes, Python глобально не устанавливается. Runner обязан предоставить Python через `actions/setup-python`.

## Логи сборки

Подробный лог:

```text
build_logs/build_YYYYMMDD_HHMMSS.log
```

Короткое машинно-читаемое резюме для ChatGPT/Codex:

```text
build_logs/last_build_summary.json
```

В резюме сохраняются этап, статус, ошибка, Python, PyInstaller, commit и путь артефакта. Сборщик хранит не более 20 подробных build-логов.

## build_info.json

Файл рядом с EXE содержит:

- версию приложения;
- commit SHA, если проект собран из Git checkout;
- версию Python;
- версию PyInstaller;
- архитектуру;
- SHA-256 EXE;
- список реально выполненных уровней проверки.

Если проект собран из ZIP без `.git`, commit отмечается как `source-archive`.

## SHA256SUMS.txt

Содержит контрольные суммы EXE и portable ZIP. Это позволяет проверить, что файлы не изменились после сборки.

## Почему используется staging

PyInstaller сначала собирает кандидата в `.build/`. `dist/` не считается результатом до тех пор, пока кандидат не прошёл source-test, packaged-test, portable-folder-test и ZIP extract-test.

Поэтому случайно появившийся `.exe` не считается готовой сборкой.

## Что можно удалить

Безопасно удалять:

```text
.build/
.build-cache/
.build-venv/
build_logs/
dist_previous/
```

При необходимости они будут созданы снова. Для запуска готовой программы достаточно содержимого `dist/`; обычно пользователю удобнее передавать `Windows-PC-Locker-portable-x64.zip`.

## Если сборка не проходит

Смотрите:

1. первое `[ERROR]` в окне;
2. `build_logs/last_build_summary.json`;
3. самый новый `build_logs/build_*.log`.

Частые причины: блокировка `pip`/python.org корпоративным proxy или антивирусом, слишком мало свободного места, отсутствие права записи в папку проекта либо блокировка свежего unsigned EXE антивирусом.

Сборщик специально не подавляет такие ошибки и не публикует непроверенный EXE как готовый.
